Executive summary

What this model does, and why it's ready

The model watches each filter's differential pressure (DP), circulation flow and flash‑drum inlet temperature, and forecasts a replacement window — a low (P10), typical (median) and high (P90) estimate of days remaining — instead of only reporting today's DP reading against a fixed alarm limit. It is retrained and validated the same way every time: on 12 complete historical fouling‑to‑replacement cycles, always tested on a cycle it has never seen, which is the same situation it faces live.

Two physical drivers explain most of why some cycles run 68 days and others run 17: flash/inlet temperature and circulation flow. Both are confirmed independently in Section 2 by direct correlation against actual cycle length — not only by the model's own internal ranking — which is the strongest form of evidence available at this data volume. Adding temperature as a model input cut the median forecast error from 5.3 to 3.2 days, the largest single improvement made to date.

The model is recommended for pilot deployment as a planning aid alongside the existing DP threshold alarms — it currently tells us both filters are healthy with roughly a month of running room. It is not yet a substitute for the alarms: with 12 cycles behind it, its confidence band is a useful planning range, not a calibrated probability (Section 6 covers this candidly, along with the two other open items worth tracking).

01Method

How the forecast is built

Five steps, run continuously from the plant historian to a live forecast.

01

Monitor DP

DPIT‑0510 (F‑510) and DPIT‑0509 (F‑509/511), read every 2 minutes from the historian.

02

Detect cycles

DP peaking ≥ 9 PSI then falling back to baseline is labeled one replacement event — 17 found historically.

03

Engineer features

DP trend, circulation flow history, flash temperature history, and DP normalized by flow.

04

Train quantile model

Gradient‑boosted regressors fit P10 / median / P90 of remaining life, validated cycle‑by‑cycle.

05

Live forecast

Current sensor readings → a predicted replacement date window, refreshed continuously.

02Evidence

2a. Within a cycle: is DP a reliable real-time signal?

Hourly correlation (Spearman) between each parameter and hours remaining until replacement, across all 10,140 training rows. This mostly confirms the obvious — DP climbs as replacement nears — which validates DP (and its trend/volatility) as the right thing to be watching moment-to-moment.

2b. Across cycles: what explains cycle length?

Pearson correlation between each parameter's cycle‑average and that cycle's actual duration, across the 12 complete cycles (6 independent periods, mirrored across both filters). This is the evidence for why temperature and flow were added as model inputs.

03Validation

How the forecast performs on cycles it never trained on

Leave-one-cycle-out validation: for each of the 12 cycles, the model is retrained on the other 11 and tested only on the one held out — never on data adjacent to what it's scoring itself against. This is the honest measure of live performance, and it's the same check re-run every time a new cycle completes.

06Known limitations

What we're watching next

None of these block a pilot deployment — they're the reason the model is positioned as a decision-support forecast running alongside existing alarms, not a replacement for them, and they define exactly what "more data" needs to fix.

Three open items

  • Sample size. 12 complete cycles is 6 independent time periods, not 12 independent samples (each period is mirrored across both filters, which share upstream conditions). Confidence-interval coverage (52.7%) will keep improving as more cycles complete — it is not expected to hit the 80% target yet.
  • Temperature–season overlap. Flash temperature correlates with cycle length (r=0.77) but also drifted upward across the data window itself (r=0.59 vs. calendar date) — cycles later in the dataset were both warmer and longer. The cross-validated accuracy gain is real and honestly measured, but confirming temperature as a true physical driver (rather than a proxy for season) needs cycles spanning a second summer and winter.
  • F-509 vs. F-511 identity. Both physical filters share a single DP tag (DPIT-0509) — there is no instrumentation anywhere in the historian that distinguishes which one is currently in service. The model treats "F-509/511" as one pooled process. Resolving this needs a manual switchover log from operations; it doesn't block the forecast, which is correct either way for "whichever filter is running."
